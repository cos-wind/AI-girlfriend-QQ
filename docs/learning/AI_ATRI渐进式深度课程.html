0. 学习地图：先建立正确的抽象

不要把这个项目理解为“一个提示词加一个模型”。更准确的模型是：外部事件进入系统后，被转换成状态；Agent 基于状态提出行动；工具产生证据或副作用；系统最终把结果编译成可交付消息。

输入OneBot 事件、引用消息、图片、语音、文件、群聊上下文
状态会话历史、用户画像、认知状态、工具回执、资源状态
输出文本、表情、语音、音乐片段和可观察日志
Event→Normalize→Context→Reason / Act→Validate→Deliver

学习时始终区分三件事：理解是对用户目标建模，执行是调用外部能力，表达是把结果变成符合人格和平台格式的回复。混在一起，就会出现工具调用不准、上下文丢失和失败后幻觉。

1. Python 运行机制：为什么要用 asyncio、线程和进程

1.1 四种任务类型

任务示例适合的执行方式
网络 I/OWebSocket 收消息、HTTP 调模型asyncio 协程
短 CPU 任务文本整理、JSON 解析直接运行或线程
阻塞本地推理OCR、embedding、模型加载asyncio.to_thread 或独立进程
重资源服务GPT-SoVITS、Ollama、NapCat独立进程和生命周期管理

1.2 事件循环的直觉

asyncio 不是让 CPU 计算变快，而是让一个线程在等待网络时去处理其他任务：

while True:
    task = ready_queue.pop()
    result = task.step()
    if task.is_waiting_io:
        io_selector.register(task)
    else:
        ready_queue.append(task)

所以模型推理、文件锁和音频处理不能直接在协程中长时间阻塞；项目使用 asyncio.to_thread() 把阻塞操作移出事件循环。

1.3 会话队列为什么重要

如果同一个用户连续发送 A、B，两次模型请求并发执行，B 可能先返回，模型还没有看到 A 的回复。按 conversation_id 建立 FIFO 队列，可以保证同一会话顺序一致，同时允许不同用户并行。

常见错误：用一个全局锁锁住所有对话，会让一个慢视觉请求阻塞所有用户；正确做法是“每会话串行 + 不同会话可并行 + 重模型另用资源锁”。

2. 分层架构：从“能运行”到“可维护”

2.1 端口与适配器思想

应用层不应该知道具体的 NapCat、Ollama 或 GPT-SoVITS。它依赖抽象契约，外部系统通过适配器接入：

OneBot Adapter→ConversationTurn←Agent Runner←Tool Adapter

application/contracts.py 中的 dataclass 就是数据端口：ConversationTurnRequest 描述输入，ArtifactEvidence 描述证据，AgentRunResult 描述 Agent 结果，DeliveryPlan 描述交付动作。

2.2 一次轮次的应用编排

request
  ↓
context_assembler(request)  # OCR、引用、记忆、RAG
  ↓
agent_runner(request, evidence)  # 模型、工具、校验
  ↓
delivery_planner(result)  # 文本/表情/语音/音乐
  ↓
TurnOutcome

ConversationTurn 的价值是把顺序和失败不变量集中在一个地方：上下文准备失败、Agent 空回复、没有交付动作，都可以被统一观察和测试。

2.3 为什么不把所有逻辑放在 persona.py

人格是领域规则的一部分，不应承担协议解析、网络请求、音频转换、数据库写入和消息分段。模块拆开后，可以单独测试“人格文本质量”“工具正确性”“OneBot 交付”和“记忆提取”。

3. Agent 框架：模型调用为什么还不等于 Agent

3.1 三个层次

LLM根据上下文预测下一段文本或结构化 tool call。
Agent Loop把模型输出、工具执行和下一轮模型请求连接起来。
Agent System再加入记忆、状态、权限、观测、重试和交付。

AI_ATRI 的 Agent 主要由自定义编排组成：AutomaticToolRunner 负责工具循环，ToolRegistry 负责能力注册，ToolReceipt 负责执行事实，CognitionKernel 负责连续状态。

3.2 ReAct、工作流和状态图

范式特点适合本项目的部分
ReAct模型在思考和行动间循环开放式搜索和工具使用
固定工作流步骤确定、易测试语音、音乐、消息交付
状态图状态显式、节点可回放认知内核和未来规划

当前设计的取舍是：旧链路继续负责生产回复；LangGraph 先以 shadow 模式观察状态。这比一次性让新图接管 QQ 副作用更容易回滚和验证。

3.3 工具调用的可靠性

模型提出 tool_call
  ├─ 解析失败：生成参数错误回执
  ├─ 执行成功：生成 ok receipt
  ├─ 执行异常：生成 failed receipt
  └─ 超过预算：禁止继续调用，要求总结
  • 工具调用次数上限：防止死循环和 token 膨胀。
  • 超时：防止一个工具拖死当前会话。
  • 权限/副作用边界：发送、点赞、发歌等动作不能只凭模型文本确认。
  • 幂等性：重复收到同一事件时，不能重复执行不可逆动作。

4. 上下文工程：模型质量的真正瓶颈

4.1 Prompt 不是越长越好

上下文的目标是让模型在有限 token 内看到“当前问题真正需要的信息”。项目把上下文分成：

  1. 稳定人格和原作设定：保持身份连续。
  2. 能力与回复合同：规定能不能调用工具、如何处理失败。
  3. 认知上下文：当前目标、情绪、未完成步骤。
  4. 相关记忆：只注入和当前问题有关的 L1/L2。
  5. 最近对话：承接省略表达和上下文。
  6. 本轮证据与工具回执：事实优先级最高。

4.2 上下文优先级

可以把上下文看成一个排序问题：当前用户指令和工具真实回执优先于旧的闲聊；明确纠正优先于模型上轮猜测；已过期事件不应覆盖当前事实。

有效上下文 = 稳定规则 + 当前目标 + 相关记忆 + 最近承接 + 真实证据

4.3 输出校验与重写

模型生成的文本不是最终结果。项目还会检查：空回复、垃圾语言、重复问题、未回答当前目标、越权声称、过长、敏感内容和视觉证据越界。第一次不合格时用较低温度和更明确的修复指令重试，连续失败再使用短兜底。

5. 记忆系统与 RAG：从存储到可用知识

5.1 三层记忆的算法意义

层机器学习视角工程规则
L1长期用户特征需要置信度、证据、冲突修正
L2时间相关事件需要时间、状态、衰减和更新
L3短期工作记忆有限窗口、滚动保留、服务当前目标

5.2 记忆提取为什么异步

回复是用户直接感知的主链路，画像更新是旁路任务。如果每条消息都同步调用记忆模型，记忆模型超时就会表现为“机器人不回复”。因此项目使用有界队列、单线程消费者和模型熔断状态。

用户消息 → 立即进入回复链路
       └→ submit(memory_request) → 后台提取 → 去重/确认 → 写入 WebUI 可见画像

5.3 FTS5 与 embedding

FTS5 更擅长精确词、专名和中文字符二元组；embedding 更擅长语义相似。余弦相似度为：

cos(q,d) = (q · d) / (||q|| × ||d||)

两路排名使用 Reciprocal Rank Fusion：

RRF(d) = Σretriever 1 / (k + rankretriever(d))

这是一种不强行比较不同检索器原始分数的融合方法，适合当前“小规模本地记忆 + 可选向量增强”的场景。

5.4 画像污染与隐私边界

群聊中必须区分 group scope 和 member scope：某个成员喜欢什么，不能自动变成整个群喜欢什么；一次玩笑也不能直接升级为 L1 事实。来源、置信度、可见范围和更新时间是画像可维护性的基础字段。

6. 多模态：OCR、视觉、视频和语音的组合

6.1 OCR 与 VLM 不是替代关系

图片→预处理→OCR：文字证据+VLM：画面语义→证据合并

“能读出图片文字”不等于“理解了图片”。OCR 的输出可以作为直接证据，视觉模型还需要判断主体、关系、表情和上下文。两者结果必须分开保存，才能在视觉模型失败时准确降级。

6.2 视频抽帧

视频理解通常不是把全部帧送入模型，而是均匀采样有限关键帧。设视频有 N 帧、采样 K 帧，位置可以近似为：

ij = round(j × (N - 1) / (K - 1)), j = 0...K-1

这样在成本、上下文长度和覆盖率之间取得平衡；快速变化场景可以进一步加入场景切分算法。

6.3 语音服务

VoiceManager 负责 QQ 侧的语音事件和交付；atri_voice_service 通过本地 HTTP 独立持有 ASR/TTS 资源。语音模型加载或超时不应拖垮文字聊天。

7. 可靠性工程：为什么系统要有这么多兜底

失败类型表现正确策略
输入失败OneBot segment 缺字段保留原始事件，降级为短文本摘要
能力失败OCR/视觉/联网超时记录 limitation，禁止补造事实
模型失败空响应、接口错误、乱码有限重试，最后短兜底
交付失败OneBot action 失败记录 action 回执，避免假装发送成功
资源失败内存不足、锁被占用释放/等待/降级，不能无限重启重模型

7.1 超时、重试和熔断

重试不是“失败了再无限试”。对可重试的网络错误进行有限次数重试；参数错误先修正参数；资源繁忙快速降级；连续模型失败后短暂熔断，避免电脑和接口被打满。

7.2 可观察性

日志是 Agent 的行为轨迹：消息接收、上下文准备、工具调用、工具回执、模型响应、交付 action 和异常都应有时间、会话 ID、工具名和耗时。

对于“不回复”，先判断事件有没有进 OneBot、是否进入队列、模型是否返回、交付 action 是否成功，再决定修哪里。

8. 由浅入深的实验路线

实验 1：手写一个最小消息管线

构造假的 ConversationTurnRequest，依次实现固定上下文、固定 Agent 和文本交付，观察 TurnOutcome。目标：理解契约而不是模型。

实验 2：实现成功/失败工具

向 ToolRegistry 注册两个工具，分别返回正常结果和异常。观察 ToolReceipt.ok 如何影响下一轮回复。

实验 3：比较三种上下文

同一个问题分别只提供最近对话、只提供 L1 记忆、提供 RAG 结果，比较模型是否能正确承接目标，并记录 token 数。

实验 4：测量 RAG

准备 20 条带标签的用户事实，构造查询集合，计算 Recall@k、Precision@k 和平均上下文长度，比较 FTS5、embedding、RRF。

实验 5：构造视觉失败

分别模拟 OCR 成功/VLM 失败、OCR 失败/VLM 成功、两者都失败，验证系统是否只输出证据覆盖的内容。

实验 6：压测资源锁

同时启动两个本地推理请求，记录等待时间、峰值内存和失败降级，确认跨进程文件锁的效果。

9. 面向 AI 专业开发者的研究方向

Agent EvaluationMemory QualityRAG RecallTool ReliabilityMultimodal GroundingResource Scheduling
  • 为工具调用建立成功率、参数修正率、平均调用轮次和伪完成率指标。
  • 为 L1/L2/L3 记忆建立准确率、冲突率、过期率和召回有效率指标。
  • 建立“用户目标是否完成”的对话级评测，而不只看回复文本相似度。
  • 为视觉回答标注 OCR 正确率、主体识别准确率和证据越界率。
  • 将 shadow cognition 与真实回复做离线 replay，比较新旧策略而不影响 QQ 运行。
  • 引入 tracing/span，把一次消息的输入、检索、模型、工具和交付串成完整调用链。

先建立可观测指标，再做架构升级。没有 replay、日志和评测集，Agent 重构很容易变成“感觉更聪明”，却无法证明更可靠。
