一、项目的核心定位

AI_ATRI 不是“收到消息后调用一次大模型”的脚本，而是一套运行在 QQ 上的本地化、多模态、带记忆和工具能力的 AI Agent 系统。

协议接入NapCat / OneBot v11 / WebSocket
Agent 编排上下文、工具、证据、输出校验
本地能力OCR、视觉、语音、SQLite RAG

设计重点不是让模型“自由发挥”，而是把模型放进可观察、可限流、可降级的工程边界中：模型负责理解和生成，工具负责执行，系统负责验证事实和安全交付。

保证消息顺序、上下文边界和发送流程。

理解目标、组织上下文、调用工具、生成和修复回复。

核心依赖方向：边缘适配层 → 应用编排层 → Agent/领域层 → 能力与基础设施层。人格层不直接发送 QQ，WebUI 不直接控制聊天连接，避免高耦合。

三、从 QQ 消息到最终回复

NapCat 事件 JSON→ 消息解析 / 引用 / 媒体归一化→ 按 conversation_id 入队→ 构造 ConversationTurnRequest
读取 L1/L2/L3 与 RAG→ AtriReplyEngine→ 模型判断是否调用工具→ 输出校验 / 降级→ MessagePlan→ OneBot action
  1. NapCat 通过反向 WebSocket 把事件推送给 OneBot 服务。
  2. message_parser.py 区分文本、引用、图片、语音、视频、文件和戳一戳。
  3. 同一会话串行处理，避免并发模型请求导致上下文乱序；不同会话可以并行。
  4. 多模态内容先变成证据，再进入模型上下文；失败时明确告诉模型能力边界。
  5. 模型直接回答，或进入有限次“模型 → 工具 → 回执 → 模型”循环。
  6. 人格引擎校验回复长度、语言、事实、隐私、人设和重复，最后编译成可发送消息。
  7. 记忆提取异步进行，不阻塞当前回复。

四、Agent 框架解析

4.1 稳定输入契约

ConversationTurnRequest 是应用层边界：conversation_id 表示对话场景，profile_id 表示用户档案，quoted_text 表示引用消息，raw_event 保留媒体和协议细节。

4.2 认知状态

状态作用工程意义
WorldState主题、实体、未解决问题、上一能力知道“现在在聊什么”
GoalState目标、约束、缺失信息、完成状态知道“用户想达成什么”
AffectiveState情绪、心情、唤醒度、信任度保持连续的互动风格
SelfState身份、价值、当前思考、近期经历维持角色连续性

CognitionKernel 目前运行在 shadow 模式：它观察并持久化状态，但不直接执行 QQ 副作用。这是兼顾新架构和旧链路稳定性的迁移策略。

4.3 关系与动作分离

relation_to_previous 描述“继续、纠正、修改、新话题”；action_domain 描述“聊天、搜索、唱歌、视觉、天气”等实际能力。例如“换一首”是修改关系，但动作领域仍是音乐。两者分离可以减少上下文丢失。

4.4 工具调用状态机

START
  ↓
请求模型
  ├── 没有 tool_calls → 规范化回复 → 输出校验 → END
  └── 有 tool_calls
        ↓
      解析工具名与 JSON 参数
        ├── 参数错误 → 写入失败回执
        ├── 执行成功 → 写入工具结果与 receipt
        └── 执行异常 → 写入短错误，禁止伪造完成
        ↓
      剩余预算足够？ → 追加回执并再次请求模型
                         → 达到上限后移除 tools，要求模型总结

工具结果是证据，不是自动结论；真实回执是“已经完成”的唯一依据。

五、记忆系统与 RAG

层级保存内容生命周期
L1稳定偏好、身份事实、沟通习惯需要确认、置信度和冲突修正
L2生日、考试、项目、计划等事件可更新、过期、休眠
L3最近几轮会话、当前话题和目标滚动窗口，不是永久画像

5.1 后台记忆提取

submit → 有界队列 → 确定性提取 → 可选模型提取 → 去重 → 写入记忆

确定性规则优先处理昵称、生日、专业等高置信事实；本地模型只做复杂语义补充。队列满、超时或模型不可用时，聊天主链路仍然可以正常回复。

5.2 双路检索

FTS5 关键词检索适合专名和明确事实；embedding 检索适合“最近总熬夜”和“作息不好”这样的语义改写。两路结果使用 RRF 合并：

RRF(d) = Σ 1 / (60 + rank(d))

系统同时限制检索条数、上下文字符数和 embedding 超时，目标是提高相关性，而不是把更多内容无差别塞进 prompt。

六、多模态、语音与资源保护

6.1 OCR 与视觉模型分工

  • OCR：输出可以核对的文字证据。
  • 视觉模型：理解主体、场景、表情包语义和画面关系。
  • 视频：有限抽帧，再合并多个画面的分析结果。
  • 回复：区分“看到了”“识别到文字”“推测”和“无法确认”。

6.2 语音进程边界

VoiceManager 负责 QQ 侧的语音事件和请求参数；atri_voice_service 通过本地 HTTP 独立持有 ASR/TTS 资源。语音模型崩溃或超时不应拖垮 OneBot 主进程。

6.3 推理资源锁

Ollama、embedding、视觉和语音可能共享内存或 GPU。项目使用跨进程文件锁，并通过 asyncio.to_thread 避免阻塞事件循环；拿不到锁时快速降级，避免同时加载多个重模型。

七、技术栈与选型

技术用途边界
Python 3.11+AI 应用、协议、文件和服务编排阻塞推理必须移出事件循环
asyncio / websocketsOneBot WebSocket 与异步消息调度需要心跳、断线和登录状态探测

Tkinter / HTTPServer桌宠、启动器、WebUI 和轻量服务适合本地运维，不是高并发网站框架

八、源码学习路线

第一阶段：理解契约

阅读 src/atri_qq_bot/application/contracts.py、turn.py、cognition/contracts.py。先弄清楚各层传递什么对象。

第二阶段：追踪普通消息

从 onebot/server.py 开始，追到 persona/core.py，最后看 message_plan/ 如何把文本意图编译为 OneBot 消息。

第三阶段：追踪工具调用

阅读 llm_tools/registry.py、llm_tools/tool_loop.py 和 application/automatic_tool_runner.py，观察参数错误、成功回执和失败回执。

第四阶段：追踪记忆与 RAG

阅读 memory_parts/core.py、memory_parts/ingestion.py、retrieval/repository.py 和 retrieval/planner.py。

第五阶段：追踪多模态与资源

阅读 toolbox.py、runtime/inference_lock.py、voice/manager.py 和 atri_voice_service/server.py。

每次学习或改动都问三个问题：数据从哪里来？状态在哪里保存？失败时怎样降级？

九、当前架构应保持的边界

  • OneBot 负责接入与发送，不负责人格判断。
  • 人格引擎负责上下文和回复，不直接操作 QQ action。
  • 工具负责证据和执行回执，不能替模型伪造事实。
  • 认知内核先 shadow 观察，再逐能力迁移真实副作用。
  • 记忆提取、向量检索和本地模型都必须可降级。
  • 新增功能优先增加“契约 + 适配器 + 测试”，不要继续把分支堆入巨型人格文件。
