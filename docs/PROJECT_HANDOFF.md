# AI_ATRI 项目交接说明

更新时间：2026-07-31

这份文档是后续开发的工程基线。新增功能、接入模型、调整回复链路前，先读本文件和对应模块代码；不要只根据表面现象添加关键词、模板或兜底分支。

## 1. 项目定位

AI_ATRI 是基于 NapCat/OneBot v11 的 QQ AI 陪伴机器人，核心目标是让亚托莉在私聊和群聊中自然回复，同时支持记忆、工具调用、图片理解、表情、语音、主动互动、桌宠和 WebUI 管理。

主要运行服务：

| 服务 | 默认地址 | 作用 |
| --- | --- | --- |
| ATRI 主服务 | `ws://127.0.0.1:8765/onebot` | 接收 NapCat 消息、回复、记忆、工具、主动互动、语音决策 |
| WebUI | `http://127.0.0.1:8787` | 配置、模型档案、记忆、表情、语音和主动互动管理 |
| 语音服务 | `http://127.0.0.1:8790` | ASR、TTS、原声素材匹配、歌唱任务 |
| Ollama | `http://127.0.0.1:11434` | 本地聊天/视觉模型 |
| GPT-SoVITS 兼容接口 | 通常为 `http://127.0.0.1:9880/tts` | 角色语音合成引擎 |

入口：

- 主机器人：`src/atri_qq_bot/__main__.py`
- 语音服务：`src/atri_voice_service/__main__.py`
- 桌宠：`src/atri_desktop/__main__.py`
- Windows 启动脚本：`tools/launch/atri/`、`tools/launch/qq_legacy/`

## 2. 总体消息链路

```text
NapCat QQ
  -> OneBotServer.handle_payload
  -> 按会话排队、去重、短暂合并
  -> should_reply / reply_mode / 群聊 @ 判断
  -> 当前消息材料解析
  -> ToolAnalyzer：时间、网页、天气、文档、图片、视频
  -> AtriReplyEngine：人设、记忆、工具循环、语言守卫、质量校验
  -> 消息规划：拆分文本、表情、语音
  -> VoiceManager / StickerManager
  -> OneBot send_*_msg
  -> 记录回复、记忆和可观测日志
```

核心边界：

- `onebot/server.py` 负责消息生命周期和外部 QQ 交互，不负责编写人设提示词。
- `toolbox.py` 负责“当前消息附带材料”的读取和分析，不负责决定最终人设回复。
- `persona/core.py` 负责把当前问题、记忆、工具结果组合成最终文本，不应伪造工具结果。
- `message_plan/` 负责把文本、表情、语音转换为可发送消息，不应重新生成内容。
- `voice/` 负责语音决策、合成、质量门和发送，不应改变正常文本回复语义。
- WebUI 只修改配置和数据文件；运行中的服务通过 `WebUIState.reload_config()` 更新可热加载配置。

## 3. 关键模块地图

### 3.1 配置和路径

- `src/atri_qq_bot/config/schema.py`：`BotConfig` 全部配置字段和默认值。
- `src/atri_qq_bot/config/loader.py`：从 `.env` 读取并校验配置；新增配置必须同时进入 schema、loader 和必要的 WebUI 映射。
- `src/atri_qq_bot/runtime/paths.py`：项目根目录、数据目录、模型档案、主动策略、语音目录等稳定路径。
- `src/atri_voice_service/config.py`：语音服务自己的配置和模型路径。

不要在业务代码里写死本机模型路径、QQ 号、API Key 或用户目录。模型根目录约定由环境变量控制，当前默认本地模型目录为 `D:\本地大模型\models`，AI_ATRI 专用语音模型默认位于其 `AI_ATRI` 子目录。

### 3.2 OneBot 和消息并发

`src/atri_qq_bot/onebot/server.py` 是系统总调度器：

- WebSocket 连接和 OneBot action 调用。
- 私聊、群聊、群内用户的会话队列。
- 消息去重、短时间合并和回复策略。
- 群聊图片先发、随后 @ 的临时材料绑定。
- 视觉上下文缓存和过期处理。
- 语音输入、语音输出、表情发送。
- 早安、空闲关怀、群聊主动互动和主动规划 v2。

重要 ID 规则：

- 私聊会话：`private:<user_id>`。
- 群聊整体会话：`group:<group_id>`。
- 群内成员档案：`group:<group_id>:user:<user_id>`。
- 私聊和群聊中的同一个人，用户档案可以统一识别，但群聊回复必须过滤私聊隐私。

不要把群聊和私聊简单合并成一条完整历史；应共享用户身份层信息，按权限决定哪些字段可以进入当前群聊提示词。

### 3.3 回复和人设

`src/atri_qq_bot/persona/core.py` 的 `AtriReplyEngine` 负责：

- 固定人设和世界观提示。
- 当前消息、近期历史、用户档案、群聊上下文。
- 工具调用后的结果注入。
- 回复质量修复、语言守卫和有限降级。
- 语音请求消费和主动消息生成。

原则：

- 人设是代码固定约束，不允许聊天内容随意改写。
- 普通情绪表达、问题、追问必须走正常 LLM 回复链路。
- 只有模型调用失败、工具失败、合成失败或明确质量门失败，才允许进入错误说明/降级链路。
- 错误说明要短，不能把长异常堆栈和模型回复文本混在一起。
- 不要用“先做最小一步”“拆成十分钟动作”之类通用模板替代真实语境回复。

### 3.4 工具系统

目录：`src/atri_qq_bot/llm_tools/`

- `time_tool.py`：当前时间。
- `web_search_tool.py`：网页搜索。
- `weather_tool.py`：天气。
- `tool_loop.py`：LLM 工具调用循环。
- `schema.py`：工具声明和参数约束。

工具调用的目标结构是：

```text
消息 -> LLM(tools=[get_current_time, search_web, ...])
     -> LLM 需要时调用工具
     -> 执行工具
     -> 工具结果回填同一轮 LLM
     -> 最终回复
```

模型应自主判断是否调用，不要在业务层用大量关键词穷举替代模型判断。业务层只负责工具契约、超时、结果校验和错误边界。

网页搜索结果必须区分“搜索到”与“能够支持当前结论”：无关结果不能作为证据。当前视觉身份核验已增加相关性检查，失败时会把身份降级为未确认。

### 3.5 材料和视觉理解

`src/atri_qq_bot/toolbox.py` 负责：

- QQ 图片、表情、文件、视频、网页和本地路径的收集。
- 文档、表格和 PDF 的文本抽取。
- 图片发送给本地视觉模型。
- 动图按时间抽取独立帧。
- 视觉结果日志和联网核验。

视觉链路的稳定约束：

1. 当前图片必须优先于旧图片、旧助手回复、用户兴趣和历史猜测。
2. 当前消息没有图片时，不能声称“看到了这张图”。
3. 群聊中“图片消息”和后续 @ 消息需要在短 TTL 内绑定。
4. 视觉模型无法确认身份时必须明确未确认，不能由旧记忆补全。
5. 聊天模型和视觉模型共用 Ollama 且显存不足时，必须串行释放和加载，不能并发硬挤显存。
6. 每次视觉请求写入 `logs/vision-events.jsonl`，记录模型、耗时、图片尺寸、准备帧数、状态和 provider 指标。

当前已验证：`qwen3-vl:8b-instruct` 能正确理解常见表情情绪和社交意图；动漫角色身份不保证全覆盖。8GB 显存下视觉模型冷加载会明显变慢，最近实测首次视觉请求约 55 秒加载、约 73 秒总耗时，这是显存串行调度的性能代价，不应通过同时常驻模型换取 OOM 或整机卡死。

### 3.6 记忆系统

- `src/atri_qq_bot/memory.py`：对外记忆存储入口。
- `src/atri_qq_bot/memory_parts/`：用户、群聊、事件、历史和档案逻辑。
- 数据主文件：`data/memory/users.json`。
- 备份目录：`data/memory/backups/`。
- WebUI 管理：`src/atri_webui/memory_admin.py`。

记忆修改必须经过持久化层和 WebUI 保存接口，不能只修改内存对象。用户资料中的爱好、习惯、好感度、活跃度和主动互动资格必须能被人工编辑，并在刷新、重启、重新进入 WebUI 后保持。

当前 WebUI 记忆面板按用户列表展示基本资料，并附带群聊信息、好感度和主动消息时间。敏感的下次主动消息时间默认隐藏，点击后才显示。

### 3.7 表情系统

- `src/atri_qq_bot/stickers.py`、`sticker_parts/`：扫描、分类、触发词、捕获和发送。
- 当前表情资源主目录：`data/stickers/`。
- 线上使用的聊天表情目录由 `.env` 的 `STICKER_DIR` 控制；不要在代码里写死用户个人图片目录。
- 触发词：`data/stickers/triggers.json`。

发送优先级应保持：人工添加素材 > 聊天记录归档 > 默认联网缓存 > URL > QQ 自带表情/emoji。

### 3.8 语音系统

QQ 侧：`src/atri_qq_bot/voice/`

- `manager.py`：ASR/TTS 调用、冷却、中文救援档案。
- `policy.py`：语音行为和概率配置。
- `segmentation.py`：长文本切段。
- `delivery.py`：发送语音。
- `calls.py`：QQ 通话邀请和会话状态。
- `client.py`：调用独立语音服务。

服务侧：`src/atri_voice_service/`

- `server.py`：HTTP 服务和 `/health`、转写、合成、歌唱任务接口。
- `speech_pipeline.py`：日常语音合成和识别。
- `providers.py`：ASR/TTS provider。
- `original_library.py`：官方原声素材匹配。
- `quality.py`：质量门。
- `singing*.py`：歌唱任务分支。
- `profiles.py`：音色档案。

语音不是文本回复的替代链路。文本已经生成后，语音策略根据明确要求、情绪、概率、好感度、活跃度、群聊开关和冷却决定是否附加语音。合成失败时要记录短错误，并按配置使用原声素材或保留文本；不能调用 Microsoft Huihui 作为隐藏最终兜底。

原声素材默认目录：`C:\Users\YOUR_NAME\Music\ATRI训练音频素材`。用户上传更多素材后，先经过索引、文本/情绪标签和匹配测试，再进入自动选择；不要未经验证就覆盖主音色模型。

### 3.9 WebUI 和模型档案

- 页面：`src/atri_webui/page.py`。
- HTTP API：`src/atri_webui/server.py`。
- 模型档案：`src/atri_webui/model_profiles.py`。
- 模型档案数据：`data/webui/model_profiles.json`。
- 主动互动策略：`data/webui/proactive_policy.json`。
- 语音行为：`data/webui/voice_behavior.json`。

模型分类是独立的：聊天模型、视觉模型、向量模型分别管理，同一类别才允许一个启用项。新增模型必须支持发现、编辑、删除、保存、启用、刷新后的持久化，并且启用前验证 provider、base URL、模型名和本地 Ollama 实际可运行状态。

本地模型扫描入口是 WebUI 的 `/api/local-models`。模型文件存在不等于 Ollama 已注册可运行；UI 必须明确区分“发现文件”和“实际可调用”。

## 4. 启动和运行约束

推荐通过现有 Windows 启动链路启动，不要重复创建新的后台终端或隐藏窗口包装层。当前 ATRI 主服务可使用：

```powershell
cd "<项目根目录>"
.venv\Scripts\pythonw.exe -m atri_qq_bot
```

启动验收顺序：

1. `8765` 监听并有 NapCat OneBot 连接。
2. `8787` WebUI 可访问。
3. `/api/test-chat` 返回 `ok=true`、`used_ai=true`。
4. 需要语音时再检查 `8790/health`，不要因为语音服务未启用阻塞主聊天。
5. 检查 Ollama 模型是否能被实际调用，不只检查模型文件是否存在。

主服务启动不应主动加载视觉模型、语音大模型或全部本地模型。重型模型按请求加载；显存不足时保持角色模型串行。

## 6. 新功能/新模型接入流程

以后每次开发必须按这个顺序走：

1. 先描述现有链路：入口、配置、运行时对象、持久化、发送出口和失败出口。
2. 明确新功能属于哪个边界：OneBot、工具、回复、人设、记忆、语音、WebUI 或独立服务。
3. 先加配置 schema、loader、WebUI 展示和持久化，再接运行时；配置要有默认值和关闭开关。
4. 新模型先做独立健康检查和最小调用，不要直接替换当前生产模型。
5. 记录模型的 provider、base URL、模型名、能力类型、显存/内存需求、上下文长度、超时和卸载策略。
6. 让模型档案按能力分类，不能因为启用视觉模型就覆盖聊天模型配置。
7. 接入真实链路前，先写单元测试：成功、超时、空结果、错误响应、旧模型不可用、模型切换和重启持久化。
8. 再做一次真实端到端测试，并保存可观测日志；不能只看到“有回复”就判定模型接入成功。
9. 失败时优先修复根因和边界，不要用关键词穷举、模板覆盖或吞异常掩盖问题。
10. 验收顺序固定为：针对性测试、全量测试、编译检查、服务重启、端口/连接检查、真实消息测试。

新模型接入最小检查表：

```text
[ ] 能否从 WebUI 看到并编辑模型档案
[ ] 模型类型是否正确：chat / vision / embedding
[ ] API 地址、模型名、鉴权是否真正可用
[ ] 是否会覆盖同类之外的模型配置
[ ] 内存/显存峰值和 keep_alive 是否测过
[ ] 超时、空输出、非 JSON、工具失败是否有明确错误
[ ] 失败是否回到正确的文本/素材链路，而不是静默模板
[ ] 重启后配置是否仍然存在
[ ] 至少一个真实请求和一组回归测试通过
```

## 7. 日志和排查入口

- OneBot 原始事件：`logs/onebot-events.log`。
- 回复链路：`logs/reply-events.jsonl`。
- 视觉分析：`logs/vision-events.jsonl`。
- 语音相关：`logs/voice-events.log` 以及语音服务自身输出。
- 工具调用：`logs/llm-tools.jsonl`。
- 记忆数据：`data/memory/users.json`。

排查顺序：

1. 先看消息是否进入 OneBot、是否被正确分配会话队列。
2. 再看 `reply-events.jsonl` 的 `used_ai`、错误和回复阶段。
3. 如果有材料，看 toolbox/vision 日志确认当前文件、模型、耗时和原始输出。
4. 如果文本正常、语音失败，只排查 VoiceManager 到语音服务的链路。
5. 如果 WebUI 修改重启后丢失，先检查 `.env`、`data/webui/*.json` 和 reload/save 接口，不要直接改内存对象。

## 8. 禁止事项

- 不要把新功能直接塞进 `server.py` 的一个超长分支，除非只是外部事件编排。
- 不要为了“看起来有回复”吞掉异常或改成固定兜底话术。
- 不要把用户私聊隐私拼进群聊提示词。
- 不要把当前图片结论交给旧记忆补全。
- 不要在未验证模型可运行前删除旧模型或旧 API 配置。
- 不要让 WebUI 只改前端显示而不写入持久化文件。
- 不要同时常驻多个高显存本地模型来换取表面速度。
- 不要在未确认工作区改动归属时回退文件。

## 9. 交接结论

这个项目现在不是“一个 Python 文件调用一个模型”，而是一个由 OneBot 入口、回复引擎、材料工具、记忆、语音独立服务、WebUI 和桌宠组成的多服务系统。稳定性的关键不是增加更多兜底模板，而是保持边界清晰、配置可持久化、模型按能力隔离、错误可观测、重型资源串行调度，并且每次改动都完成真实链路验收。
